# Host HPO qualification across bindings

The native HPO contract and an operator's implementation are separate claims. DAG-ML owns trial scheduling, fold identity, native scoring, pruning, selection, and checkpoint validation. Each host owns model fitting and predictions. A passing JSONL handshake or a callback that returns fabricated predictions qualifies the protocol, not a real host model.

For the first shared real-operator matrix, use a small seeded regression dataset, a published two-fold `FoldSet`, and a closed two- or three-value regularization grid. Implement the same ridge objective in Python, R, Octave/MATLAB, and JS using each host's local linear-algebra library, or use a Methods PLS controller where that binding exists. Require every binding to report the same sample IDs, per-fold predictions, native fold scores, trial states and order, winner, full-train refit predictions, and a replayable artifact. Allow documented floating-point tolerances for different solvers. Run one uninterrupted search and one interrupted/resumed search with parallel trials and a pruning case. A test must fail rather than silently substitute a synthetic controller when its language runtime or model implementation is required in CI.

The current local environment has Node, Chrome, and R through Miniconda, but lacks Octave/MATLAB. The R Ridge oracle exercises a real local model against native fold scoring; `python3 dag-ml/scripts/test_hpo_language_adapters.py` checks protocol forwarding and may skip runtimes absent from `PATH` unless their required-runtime gates are enabled. DAG-ML CI requires R, Octave, and browser protocol gates and a real R Ridge operator gate. Node and Chrome ridge smokes prove real JS operators on those surfaces; Octave/MATLAB local operators, broader R operators, and R/JS full-train REFIT and artifact replay remain open. `feature_gaps.json` retains `inventory_complete=false` while other feature gaps remain.
